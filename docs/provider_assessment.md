## 2. აუთენტიკაციის მეთოდების გადამოწმება და შერჩევა

### მოთხოვნები
- მრავალფაქტორიანი აუთენტიკაცია (MFA) კრიტიკულ ადმინისტრაციულ და მომხმარებლის ანგარიშებზე.
- OAuth 2.0 / OpenID Connect მხარდაჭერა მესამე მხარის ინტეგრაციებისთვის.
- SAML 2.0 საწარმოო პარტნიორებისთვის.
- WebAuthn/FIDO2 მხარდაჭერა უმაღლესი უსაფრთხოებისთვის.
- აღრიცხვისა და მონიტორინგის ინტეგრაცია (SIEM export, audit logs).

### შეფასება
- **AWS Cognito**: მხარს უჭერს OAuth 2.0/OIDC, SAML, MFA (TOTP, SMS); WebAuthn ხელმისაწვდომი "Advanced Security" ფუნქციით. Log export CloudWatch/SIEM.
- **Azure AD B2C**: სრულ მხარდაჭერას უწევს OAuth/OIDC, SAML, Conditional Access MFA, FIDO2/WebAuthn. Log export Azure Monitor/Sentinel.
- **GCP Identity Platform**: OAuth/OIDC, MFA (SMS/Authenticator App), ჯერ არ აქვს სრული SAML, WebAuthn beta. ლოგები Stackdriver-ში.
- **Auth0**: ფართო მხარდაჭერა OAuth/OIDC, SAML, MFA (SMS, push, WebAuthn). შემქმნელებისთვის მოქნილი.

### შერჩეული ვარიანტი
- **ძირითადი პროვაიდერი**: *Azure AD B2C* – უპირატესობა Conditional Access, FIDO2 მხარდაჭერა, ინტეგრირებული შესაბამისობა (GDPR, ISO 27001).
- **რეზერვული/ჰიბრიდული ვარიანტი**: *Auth0* – სწრაფი დანერგვა, მრავალფეროვანი SDK.
- მოთხოვნის შემთხვევაში შესაძლებელია AWS Cognito კონკრეტული AWS ინფრასტრუქტურის პროექტებისთვის.

## 3. მონაცემთა შენახვის პოლიტიკა და წაშლის წესები

### სისტემაში (აპლიკაციის შიდა ინფრასტრუქტურა)
- **მონაცემთა კლასიფიკაცია**: საჯარო, შიდა, კონფიდენციალური (PII), მაღალკონფიდენციალური.
- **შენახვა**: კონფიდენციალური მონაცემები დაშიფრულია (AES-256 at rest, TLS 1.2+ in transit). ლოგიკურად განცალკევებული პროდ/ტესტი.
- **Retention**: PII მაქსიმუმ 24 თვე, თუ რეგულაცია არ მოითხოვს მეტს.
- **წაშლა**: მომხმარებლის მოთხოვნისთანავე 30 დღეში სრული წაშლა (primary + backups) GDPR Article 17 შესაბამისად.

### პროვაიდერთან (Azure AD B2C/Auth0)
- დამხმარე ხელშეკრულებაში ჩავრთოთ Data Processing Addendum (DPA).
- მონაცემთა რეზიდენცია: არჩევა EU რეგიონში.
- Logs/events როტაცია 90 დღეში; რეგულარული ექსპორტი საკუთარ SIEM-ში.
- წაშლის პროცედურა: API کالით ანგარიშისა და ატრიბუტების გაწმენდა; პროვაიდერის მხარდაჭერით backup წაშლის დადასტურება.

### ლოგები
- აპლიკაციური ლოგები შეიცავს მინიმალურ პერსონალურ ინფორმაციას (token identifiers). Pseudonymization.
- Retention 90 დღე ოპერაციული მიზნებისთვის, 12 თვე უსაფრთხოების ინციდენტების გამოძიებისთვის დაცული საცავში.
- წაშლა ავტომატური როტაციით და არქივების დაშიფვრა.

## 4. რეგულაციები და შესაბამისობის მოთხოვნები

- **GDPR (EU)**: მონაცემთა დამუშავების სამართლებრივი საფუძველი, Data Subject Access Requests (DSAR) 30 დღეში, Data Protection Impact Assessment (DPIA) მაღალი რისკის პროცესებისთვის, Data Breach Notification 72 საათში.
- **საქართველოს კანონი პერსონალურ მონაცემთა დაცვაზე**: მინიმალური მონაცემების დამუშავება, უსაფრთხოების ზომები, ინფორმირებული თანხმობა, პერსონალური მონაცემების ინსპექციასთან თანამშრომლობა.
- **ISO/IEC 27001** (სურვილისამებრ): ინფორმაციული უსაფრთხოების მართვის სისტემა.
- **PCI-DSS** (თუ ფინანსური ტრანზაქციები): კარტის მონაცემების სეგმენტაცია, ვალდებულებების განსაზღვრა.
- შესასრულებელია Vendor Risk Assessment და ყოველწლიური აუდიტი.

## 5. შეთანხმება მხარეებთან და დოკუმენტირება

- **შეხვედრები**: უსაფრთხოების გუნდი, იურიდიული დეპარტამენტი, DevOps/ინფრასტრუქტურა, პროდუქტის მენეჯმენტი.
- **გადაწყვეტილებები**:
  - ავირჩიოთ Azure AD B2C როგორც ძირითადი იდენტობის პროვაიდერი EU რეგიონში.
  - დავამზადოთ DPA და SLA დანართები, შევთანხმდეთ ფასზე და მინიმალურ ხელმისაწვდომობის მოთხოვნაზე (>=99.9%).
  - ჩავწეროთ მონაცემთა შენახვის პოლიტიკა კომპანიის უსაფრთხოების სახელმძღვანელოში.
  - განვაახლოთ ინციდენტების რეაგირების გეგმა GDPR 72-საათიანი წესიით.
  - დავნიშნოთ გადამოწმება ყოველ 12 თვეში და ცვლილებების მართვის პროცესი.
- **დოკუმენტაცია**: შევინახოთ ეს დოკუმენტი Confluence/SharePoint-ზე, გავუზიაროთ მხარეებს, დავამატოთ ხელმოწერილი შეთანხმებები კონტრაქტების საცავში.
